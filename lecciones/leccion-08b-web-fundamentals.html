Fase 2 — Pentesting Fundamental

Fundamentos de Desarrollo Web — Lo que necesitas antes de hackear webs

Antes de aprender a explotar vulnerabilidades web como SQL Injection o XSS, necesitas entender cómo funciona una aplicación web por dentro. En esta lección aprenderás qué hacen HTML, JavaScript y CSS, cómo el navegador se comunica con el servidor mediante HTTP, qué es una base de datos relacional y cómo todo se conecta en el flujo de una petición real.

1. ¿Cómo funciona una aplicación web?

Una aplicación web no es un programa que instalas en tu PC — vive en un servidor remoto y tú la usas a través del navegador. Cada vez que abres Facebook, Gmail o tu banco online, tu navegador se conecta a un servidor que procesa tu petición y te devuelve una página.

Analogía: El restaurante

Una app web funciona como un restaurante: tú (el cliente/navegador) pides un platillo al mesero (el protocolo HTTP). El mesero lleva tu pedido a la cocina (el servidor). El chef consulta la receta (la base de datos), prepara el platillo y el mesero te lo trae. Si el chef no valida lo que le pides, podrías pedirle que te dé la receta secreta — eso es básicamente una inyección SQL. 

    ┌──────────┐     HTTP Request      ┌──────────────┐     Query      ┌────────────┐
    │          │ ──────────────────────►│              │ ──────────────►│            │
    │ CLIENTE  │                        │  SERVIDOR    │                │  BASE DE   │
    │(Navegador)│◄──────────────────────│  (Backend)   │◄──────────────│   DATOS    │
    │          │     HTTP Response      │  PHP/Python/ │    Resultados  │  (MySQL,   │
    │ HTML+CSS │                        │  Node.js     │                │  PostgreSQL│
    │   + JS   │                        │              │                │  etc.)     │
    └──────────┘                        └──────────────┘                └────────────┘

Arquitectura Cliente → Servidor → Base de Datos

ComponenteDónde viveQué hace
FrontendEn tu navegador (cliente)Lo que VES: diseño, formularios, botones, animaciones. Se ejecuta en TU máquina.
BackendEn el servidor remotoLa LÓGICA: procesa datos, verifica credenciales, consulta la base de datos.
Base de datosEn el servidor (o un servidor dedicado)Almacena DATOS: usuarios, contraseñas, productos, mensajes.

2. HTML, CSS y JavaScript: los tres pilares

Todo lo que ves en tu navegador está construido con tres tecnologías que trabajan juntas:

TecnologíaFunciónAnalogía
HTMLLa estructura de la página: títulos, párrafos, formularios, links, imágenes.Los cimientos y paredes de una casa
CSSEl diseño visual: colores, fuentes, layout, animaciones.La pintura y decoración de la casa
JavaScriptEl comportamiento: interactividad, validación, comunicación con el servidor sin recargar.La electricidad e instalaciones que hacen que todo funcione

HTML: la estructura

Ejemplo de HTML — Formulario de login
<!-- Un formulario de login típico -->
<form action="/login" method="POST">
    <input type="text" name="username" placeholder="Usuario">
    <input type="password" name="password" placeholder="Contraseña">
    <button type="submit">Iniciar Sesión</button>
</form>

<!-- Lo importante para hacking web: -->
<!-- action="/login"  → A dónde se envían los datos -->
<!-- method="POST"    → Cómo se envían (POST = en el body, no en la URL) -->
<!-- name="username"  → El nombre del campo que recibe el servidor -->

¿Por qué importa? Cuando haces SQL Injection, escribes código malicioso en estos campos input. El valor de name te dice qué parámetro manipular. El method y action te dicen cómo y adónde viajan los datos.

JavaScript: el comportamiento

JavaScript en el navegador
// JavaScript puede manipular la página (DOM)
document.getElementById("username").value = "admin";

// Puede hacer peticiones al servidor sin recargar (AJAX/Fetch)
fetch('/api/users/123')
    .then(response => response.json())
    .then(data => console.log(data));

// Puede acceder a cookies
console.log(document.cookie);
// → "session=abc123; token=xyz789"

// ¿Por qué importa? Un ataque XSS inyecta JavaScript malicioso
// que puede robar cookies con: document.cookie

Clave para entender XSS

Cross-Site Scripting (XSS) funciona porque el atacante logra que su código JavaScript se ejecute en el navegador de la víctima. Si la app web no sanitiza los datos, un atacante puede inyectar <script>document.cookie</script> y robar la sesión del usuario.

3. HTTP en detalle: métodos, headers y cookies

HTTP (HyperText Transfer Protocol) es el idioma que hablan el navegador y el servidor. Cada interacción es una petición (request) y una respuesta (response).

Métodos HTTP principales

MétodoUsoEjemplo
GETPedir información. Los parámetros van en la URL.GET /buscar?q=hacking
POSTEnviar datos al servidor. Los parámetros van en el body (no en la URL).POST /login con body: user=admin&pass=123
PUTActualizar un recurso existente.PUT /api/users/5
DELETEEliminar un recurso.DELETE /api/users/5

Anatomía de una petición HTTP

Petición HTTP real (lo que ve Burp Suite)
POST /login HTTP/1.1
Host: www.ejemplo.com
Content-Type: application/x-www-form-urlencoded
Cookie: session=abc123def456
User-Agent: Mozilla/5.0 (X11; Linux x86_64)

username=admin&password=MiContraseña123

--- RESPUESTA DEL SERVIDOR ---
HTTP/1.1 302 Found
Set-Cookie: session=nuevo_token_xyz789; HttpOnly; Secure
Location: /dashboard

Lo importante: La línea Cookie: contiene tu sesión. Si un atacante la roba (vía XSS), puede suplantar tu identidad. Set-Cookie crea cookies nuevas. HttpOnly impide que JavaScript acceda a la cookie.

Cookies y sesiones

HTTP es stateless (sin estado) — cada petición es independiente. Para "recordar" que estás logueado, el servidor te da una cookie de sesión: un token que tu navegador envía en cada petición. Si alguien roba tu cookie, puede actuar como tú sin conocer tu contraseña.

4. Bases de datos relacionales y SQL

La mayoría de aplicaciones web guardan información en bases de datos relacionales: tablas con filas y columnas, como una hoja de Excel muy poderosa. SQL (Structured Query Language) es el lenguaje que se usa para consultar y manipular esos datos.

Analogía: La base de datos es un archivo de Excel

Imagina una hoja de Excel llamada "usuarios" con columnas: id, nombre, email, password_hash. SQL es el idioma para preguntarle cosas a ese Excel: "dame todos los usuarios cuyo email contenga @gmail.com" o "agrega una nueva fila". SQL Injection es cuando el atacante logra escribir sus propias instrucciones SQL en lugar de solo un nombre de usuario.

Tabla de ejemplo: users

idusernameemailpassword_hashrole
1adminadmin@empresa.com5f4dcc3b5aa765d61...admin
2jgarciajuan@empresa.come99a18c428cb38d5f...user
3mlopezmaria@empresa.comd8578edf8458ce06f...user

Comandos SQL esenciales

SQL básico — Lo mínimo para entender SQLi
-- SELECCIONAR datos (leer)
SELECT * FROM users;                       -- Todos los usuarios
SELECT username, email FROM users WHERE role = 'admin';  -- Solo admins

-- INSERTAR datos (crear)
INSERT INTO users (username, email, password_hash, role)
VALUES ('nuevo', 'nuevo@mail.com', 'hash123', 'user');

-- ACTUALIZAR datos
UPDATE users SET role = 'admin' WHERE username = 'jgarcia';

-- BORRAR datos
DELETE FROM users WHERE id = 3;

-- UNIR tablas
SELECT users.username, orders.total 
FROM users JOIN orders ON users.id = orders.user_id;

¿Por qué importa? SQL Injection funciona porque la aplicación construye estas consultas concatenando lo que escribes en el formulario. Si escribes ' OR '1'='1' -- en lugar de un nombre de usuario, alteras la lógica de la consulta.

Cómo funciona un login con SQL (código vulnerable)

Login vulnerable vs. seguro
❌ CÓDIGO VULNERABLE (NO hagas esto):
query = "SELECT * FROM users WHERE username='" + user_input + "' AND password='" + pass_input + "'"

# Si el atacante escribe: admin' OR '1'='1' -- 
# La query se convierte en:
SELECT * FROM users WHERE username='admin' OR '1'='1' --' AND password=''
# '1'='1' siempre es verdadero → el atacante entra como admin

CÓDIGO SEGURO (parametrizado):
query = "SELECT * FROM users WHERE username = %s AND password = %s"
cursor.execute(query, (user_input, pass_input))
# Los parámetros se tratan como DATOS, nunca como código SQL

5. El flujo completo: del formulario a la base de datos

Ahora que conoces cada pieza, veamos cómo se conectan en un escenario real: un usuario hace login en una aplicación web. 

    1. El usuario escribe usuario/contraseña en el formulario HTML
       └─→ El navegador construye una petición HTTP POST

    2. POST /login HTTP/1.1
       Body: username=jgarcia&password=MiPass123
       └─→ Se envía al servidor vía HTTP (cifrado si es HTTPS)

    3. El servidor recibe los datos
       └─→ El backend (PHP/Python/Node.js) los procesa

    4. El backend construye una consulta SQL:
       SELECT * FROM users WHERE username='jgarcia' AND password_hash='...'
       └─→ Envía la query a la base de datos

    5. La base de datos responde:
       └─→ ✓ "Encontré al usuario" → El servidor crea una cookie de sesión
       └─→ ✗ "No encontrado" → El servidor responde "Credenciales inválidas"

    6. El servidor envía la respuesta HTTP al navegador:
       HTTP 302 Found + Set-Cookie: session=TOKEN_UNICO
       └─→ El navegador guarda la cookie y redirige al dashboard

Flujo completo de un login web: Formulario → HTTP → Backend → SQL → Respuesta

⚠️ ¿Dónde vive cada vulnerabilidad?

SQL Injection: En el paso 4 — si el backend concatena los datos sin sanitizar.
XSS: En el paso 6 — si el servidor refleja datos del usuario sin escapar en el HTML.
CSRF: En el paso 2 — si la app no verifica que la petición fue iniciada por el usuario real.
IDOR: En el paso 3 — si el backend no verifica que el usuario tiene permiso de acceder al recurso.
