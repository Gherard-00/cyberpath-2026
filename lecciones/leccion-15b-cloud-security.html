Cloud Security 101 — Seguridad en AWS, Azure y GCP

El 94% de las empresas usan servicios en la nube. Las infraestructuras ya no viven solo en servidores físicos — ahora están en AWS, Azure y Google Cloud. Como pentester moderno, necesitas entender cómo funciona la nube, dónde se cometen errores y cómo se explotan. En esta lección aprenderás los conceptos fundamentales de cloud security, los ataques más comunes y las herramientas para auditarlos.

1. ¿Qué es "la nube" realmente?

"La nube" no es magia — son computadoras de otra persona. Específicamente, son centros de datos masivos operados por Amazon (AWS), Microsoft (Azure) o Google (GCP) que te alquilan servidores, bases de datos, almacenamiento y servicios a demanda.

Analogía: Hotel vs. Casa propia

Tener tu propio servidor es como tener casa propia: tú controlas todo, pero también mantienes todo (plomería, electricidad, seguridad). La nube es como vivir en un hotel: ellos mantienen la estructura, pero tú eres responsable de no dejar la puerta de tu habitación abierta. La mayoría de las brechas en la nube ocurren porque el cliente dejó "la puerta abierta" — no porque el hotel fue hackeado.

2. Modelo de responsabilidad compartida

Este es el concepto más importante de cloud security. Define quién es responsable de qué. 

    ┌─────────────────────────────────────────────────────────────┐
    │                RESPONSABILIDAD DEL CLIENTE                   │
    │                                                              │
    │   ✓ Datos y contenido                                        │
    │   ✓ Gestión de identidades (IAM)                             │
    │   ✓ Configuración de seguridad de servicios                  │
    │   ✓ Cifrado de datos (en reposo y en tránsito)               │
    │   ✓ Firewall / Security Groups / NACLs                       │
    │   ✓ Parches del OS (en IaaS)                                 │
    ├──────────────────────────────────────────────────────────────┤
    │              RESPONSABILIDAD DEL PROVEEDOR                   │
    │                                                              │
    │   ✓ Seguridad física del data center                         │
    │   ✓ Hardware, networking, virtualización                     │
    │   ✓ Infraestructura global                                   │
    │   ✓ Servicios fundamentales (compute, storage, DB)           │
    └─────────────────────────────────────────────────────────────┘

Seguridad DE la nube (proveedor) vs. Seguridad EN la nube (cliente)

⚠️ La realidad de las brechas cloud

Según Gartner, el 99% de los fallos de seguridad en la nube serán culpa del cliente, no del proveedor. Los errores más comunes: buckets S3 públicos, credenciales IAM excesivamente permisivas, security groups abiertos a 0.0.0.0/0, y secretos hardcodeados en código.

3. IAM: Identity and Access Management

IAM es el sistema de control de acceso de la nube. Define quién puede hacer qué sobre qué recursos. Es el equivalente cloud de Active Directory.

Analogía: El sistema de pases de un festival

IAM funciona como los pases de un festival de música: hay pases generales (acceso básico), VIP (más recursos), y backstage (admin total). Si alguien pierde su pase VIP o lo clona, tiene acceso a zonas que no debería. Y si el festival da pases backstage a todos "por comodidad"... cualquiera puede llegar al escenario.

Ejemplo de política IAM (AWS)

Política IAM peligrosa vs. segura
❌ PELIGROSO — Acceso total a todo (AdministratorAccess):
{
    "Version": "2012-10-17",
    "Statement": [{
        "Effect": "Allow",
        "Action": "*",           ← Cualquier acción
        "Resource": "*"         ← Sobre cualquier recurso
    }]
}

SEGURO — Principio de mínimo privilegio:
{
    "Version": "2012-10-17",
    "Statement": [{
        "Effect": "Allow",
        "Action": [
            "s3:GetObject",
            "s3:ListBucket"
        ],
        "Resource": [
            "arn:aws:s3:::mi-bucket-datos",
            "arn:aws:s3:::mi-bucket-datos/*"
        ]
    }]
}

Principio de mínimo privilegio: Cada usuario/servicio solo debe tener los permisos estrictamente necesarios para su función. Nunca uses Action: "*" en producción.

4. Almacenamiento expuesto: el error #1 en la nube

El servicio de almacenamiento de objetos (AWS S3, Azure Blob Storage, Google Cloud Storage) es donde se guardan archivos: backups, logs, datos de usuarios, assets. El error más común es dejarlo público accidentalmente.

ProveedorServicioURL pública típica
AWSS3 Buckethttps://nombre-bucket.s3.amazonaws.com/
AzureBlob Storagehttps://cuenta.blob.core.windows.net/container/
GCPCloud Storagehttps://storage.googleapis.com/nombre-bucket/

Cómo buscar buckets expuestos

Enumeración de buckets S3
# Verificar si un bucket existe y es accesible
$ curl -s https://nombre-empresa.s3.amazonaws.com/ | head

# Listar contenido de un bucket público con AWS CLI
$ aws s3 ls s3://nombre-empresa --no-sign-request

# Descargar todo el contenido de un bucket público
$ aws s3 sync s3://nombre-empresa ./bucket-dump --no-sign-request

# Google dorking para encontrar buckets expuestos
# site:s3.amazonaws.com "nombre-empresa"
# site:blob.core.windows.net "nombre-empresa"

Brechas reales: Capital One (2019) — 100 millones de registros expuestos por un bucket S3 mal configurado. Accenture, FedEx, Pentagon — todos han tenido datos expuestos en S3 públicos.

5. Vectores de ataque comunes en la nube

AtaqueDescripciónCómo se previene
Credenciales expuestasClaves de API/access keys hardcodeadas en código (GitHub, .env)AWS Secrets Manager, Azure Key Vault, rotación automática
Buckets públicosStorage accesible sin autenticaciónBlock Public Access, bucket policies restrictivas
Security Groups abiertosPuertos abiertos a 0.0.0.0/0 (todo Internet)Restringir a IPs específicas, usar VPN
SSRF → MetadataServer-Side Request Forgery para acceder al servicio de metadata (169.254.169.254) y robar credenciales temporalesIMDSv2, WAF, validación de URLs
Privilege Escalation IAMPermisos excesivos permiten crear nuevos admins o asumir roles más privilegiadosMínimo privilegio, auditoría regular de políticas
Lambda/Functions abuseFunciones serverless con permisos excesivos o inyección de comandosRoles con mínimo privilegio, input validation

SSRF al servicio de metadata — El ataque más peligroso en la nube

Cada instancia EC2/VM tiene acceso a un servicio de metadata en http://169.254.169.254. Si una aplicación web tiene SSRF, el atacante puede hacer que el servidor consulte esa URL interna y obtenga credenciales temporales de IAM. Con esas credenciales, puede acceder a S3, bases de datos, y cualquier recurso que el rol de la instancia permita. Así fue exactamente el ataque a Capital One.

Comandos de reconocimiento AWS
# Verificar quién eres (con credenciales comprometidas)
$ aws sts get-caller-identity

# Listar buckets S3
$ aws s3 ls

# Listar instancias EC2
$ aws ec2 describe-instances --region us-east-1

# Listar usuarios IAM
$ aws iam list-users

# Ver políticas de un usuario
$ aws iam list-attached-user-policies --user-name nombre

# Acceder al servicio de metadata (desde dentro de una EC2)
$ curl http://169.254.169.254/latest/meta-data/iam/security-credentials/
