Fase 5 — Profesionalización y Nivel Experto

Elaboración de Informes Profesionales de Auditoría

Puedes ser el mejor hacker del mundo, pero si no sabes comunicar tus hallazgos, tu trabajo no tiene valor. El informe de auditoría es el producto final que entregas al cliente. Un buen informe convierte hallazgos técnicos en decisiones de negocio. En esta lección aprenderás a escribir informes profesionales que te harán destacar en la industria.

📝 1. ¿Por qué importa el informe?

📌 Realidad de la industria:
  • El cliente no ve tu terminal ni tus comandos. Solo ve tu informe.
  • El informe es lo que justifica tu precio. Un informe de 3 páginas no justifica $50,000.
  • El informe es el que convence al CTO de invertir $500,000 en seguridad.
  • Un informe mal escrito puede hacer que nadie tome acción, aunque hayas encontrado vulnerabilidades críticas.
  • El informe es evidencia legal — debe ser preciso, profesional y verificable.

👥 2. Conoce a tu audiencia

Tu informe lo leerán diferentes personas con diferentes necesidades. Debes escribir para todos:

AudienciaLo que quiere saberSección del informe
CEO / Directivos"¿Estamos en riesgo? ¿Cuánto nos cuesta?" (no quieren detalles técnicos)Resumen ejecutivo
CISO / Security Manager"¿Qué tan grave es? ¿Qué arreglamos primero?"Clasificación de riesgos + prioridades
Equipo técnico (IT/Dev)"¿Exactamente qué está mal y cómo lo arreglo?"Fichas técnicas + remediación detallada
Legal / Compliance"¿Cumplimos con la normativa? ¿Hay implicaciones legales?"Alcance, metodología, cumplimiento

📋 3. Estructura del informe profesional

    Estructura recomendada:
    
    1. PORTADA
       └── Nombre del proyecto, cliente, fecha, clasificación
    
    2. ÍNDICE
    
    3. RESUMEN EJECUTIVO (1-2 páginas)
       └── Para directivos. Sin jerga técnica.
    
    4. ALCANCE Y METODOLOGÍA
       └── Qué se probó, qué NO se probó, metodología usada
    
    5. CLASIFICACIÓN DE RIESGOS
       └── Resumen visual: cuántas críticas, altas, medias, bajas
    
    6. HALLAZGOS DETALLADOS
       └── Una ficha técnica por cada vulnerabilidad
    
    7. GUÍA DE REMEDIACIÓN PRIORIZADA
       └── Qué arreglar primero y cómo
    
    8. CONCLUSIONES
    
    9. ANEXOS
       └── Evidencias adicionales, logs completos, herramientas usadas

📊 4. Cómo escribir el resumen ejecutivo

El resumen ejecutivo es la sección más importante. Muchos directivos SOLO leerán esta página. Debe responder tres preguntas:

📌 Las 3 preguntas del resumen ejecutivo:
  1. ¿Qué encontramos? — "Identificamos 23 vulnerabilidades, de las cuales 3 son críticas"
  2. ¿Cuál es el impacto real? — "Un atacante podría acceder a la base de datos de 50,000 clientes"
  3. ¿Qué debe hacer la organización? — "Recomendamos priorizar las 3 vulnerabilidades críticas en los próximos 30 días"
✅ Ejemplo de buen resumen ejecutivo:

"Durante la auditoría de seguridad realizada entre el 1 y el 15 de julio de 2026, se evaluó la infraestructura externa e interna de [Empresa]. Se identificaron 23 vulnerabilidades: 3 críticas, 7 altas, 8 medias y 5 informativas. Las vulnerabilidades críticas permitirían a un atacante externo obtener acceso completo al servidor de base de datos que contiene información personal de 50,000 clientes, lo que podría resultar en una multa por incumplimiento de la Ley de Protección de Datos de hasta $2M. Se recomienda remediar las 3 vulnerabilidades críticas en un plazo máximo de 30 días."

❌ Ejemplo de MAL resumen:

"Se encontraron varias vulnerabilidades de tipo SQL injection en el parámetro id del endpoint /api/users usando payload ' OR 1=1-- con Burp Suite v2024.3 y también un XSS reflejado en..."

→ Demasiado técnico. Un CEO no sabe qué es SQL injection ni Burp Suite.

📈 5. Clasificar vulnerabilidades con CVSS

CVSS (Common Vulnerability Scoring System) es el estándar para medir la severidad de una vulnerabilidad en una escala de 0.0 a 10.0.

PuntuaciónSeveridadColorPlazo de remediación sugerido
9.0 – 10.0🔴 CríticaRojoInmediato (24-72 horas)
7.0 – 8.9🟠 AltaNaranja1-2 semanas
4.0 – 6.9🟡 MediaAmarillo1-3 meses
0.1 – 3.9🟢 BajaVerdeSiguiente ciclo de mantenimiento
0.0ℹ️ InformativaAzulMejora recomendada, no urgente
📌 Métricas CVSS v3.1:
  • Attack Vector (AV): ¿Desde dónde se explota? Network / Adjacent / Local / Physical
  • Attack Complexity (AC): ¿Qué tan fácil es? Low / High
  • Privileges Required (PR): ¿Necesitas autenticación? None / Low / High
  • User Interaction (UI): ¿Necesitas que el usuario haga algo? None / Required
  • Scope (S): ¿Afecta a otros componentes? Unchanged / Changed
  • Confidentiality (C): ¿Se filtra información? None / Low / High
  • Integrity (I): ¿Se pueden modificar datos? None / Low / High
  • Availability (A): ¿Se puede tirar el servicio? None / Low / High

Calculadora oficial: first.org/cvss/calculator/3.1

🗂️ 6. Fichas técnicas de hallazgos

Cada vulnerabilidad encontrada debe documentarse con una ficha técnica estandarizada:

    ┌─────────────────────────────────────────────────────────┐
    │  HALLAZGO #001                                         │
    │  SQL Injection en formulario de login                   │
    ├─────────────────────────────────────────────────────────┤
    │  Severidad:    🔴 CRÍTICA (CVSS 9.8)                    │
    │  CVSS Vector:  AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H    │
    │  Activo:       app.empresa.com/login                     │
    │  Parámetro:    username                                  │
    │  CWE:          CWE-89 (SQL Injection)                    │
    ├─────────────────────────────────────────────────────────┤
    │  DESCRIPCIÓN:                                           │
    │  El parámetro "username" del formulario de login no      │
    │  sanitiza la entrada del usuario, permitiendo inyectar   │
    │  sentencias SQL que extraen toda la base de datos.       │
    ├─────────────────────────────────────────────────────────┤
    │  EVIDENCIA:                                              │
    │  [Screenshot de Burp Suite mostrando el payload]         │
    │  [Request/Response completos]                            │
    │  [Datos extraídos (censurados)]                          │
    ├─────────────────────────────────────────────────────────┤
    │  IMPACTO:                                                │
    │  Un atacante sin autenticación puede extraer todos los   │
    │  datos de la base de datos: usuarios, contraseñas,       │
    │  información personal de 50,000 clientes.                │
    ├─────────────────────────────────────────────────────────┤
    │  REMEDIACIÓN:                                            │
    │  1. Usar consultas parametrizadas (prepared statements)  │
    │  2. Implementar WAF como capa adicional                  │
    │  3. Aplicar principio de mínimo privilegio al DB user    │
    │  Referencia: OWASP SQL Injection Prevention Cheat Sheet  │
    └─────────────────────────────────────────────────────────┘

📸 7. Cómo presentar evidencias

📌 Reglas de oro para evidencias:
  • ✅ Cada hallazgo debe tener al menos un screenshot
  • ✅ Resaltar lo importante: usa flechas rojas y recuadros
  • ✅ Mostrar Request Y Response: no solo el resultado, sino cómo lo lograste
  • ✅ Censurar datos sensibles: nunca incluir contraseñas reales, datos de clientes, o información PII sin censurar
  • ✅ Numerar cada screenshot: "Figura 3.1: Inyección SQL exitosa en /login"
  • ✅ Incluir timestamps: cuándo se descubrió y reproduce la vulnerabilidad
  • ❌ NO incluir screenshots de tu escritorio con información personal visible
  • ❌ NO incluir datos extraídos completos (solo muestras censured)

🔧 8. Guías de remediación

La remediación debe ser específica, accionable y priorizada:

PrioridadHallazgoRemediaciónEsfuerzoPlazo
🔴 1SQL Injection en loginImplementar prepared statements en auth.php línea 452-4 horas24h
🔴 2RCE en upload de archivosValidar extensión + MIME type + renombrar archivos4-8 horas48h
🟠 3XSS reflejado en búsquedaEscapar output con htmlspecialchars()1-2 horas1 semana
🟡 4Headers de seguridad faltantesAgregar CSP, HSTS, X-Frame-Options en nginx.conf1 hora2 semanas
💡 Tip profesional: No digas solo "arreglar la vulnerabilidad". Di exactamente cómo, en qué archivo, en qué línea, con un ejemplo de código corregido si es posible. Esto diferencia a un pentester junior de un profesional.

⚠️ 9. Errores comunes a evitar

ErrorProblemaSolución
Solo listar CVEsNo explica el impacto real para la empresaContextualizar: "Esto permite que un atacante acceda a..."
Resumen muy técnicoEl CEO no entiende nada y no toma acciónEscribir el resumen ejecutivo en lenguaje de negocio
Sin priorizaciónEl equipo técnico no sabe por dónde empezarOrdenar hallazgos por severidad + tabla de remediación priorizada
Screenshots sin contextoNo se entiende qué se está mostrandoDescribir cada screenshot con texto debajo
Remediación genérica"Mejorar la seguridad" no es accionableDar pasos específicos con código, configuración, y referencias
Errores gramaticalesResta credibilidad profesionalRevisar ortografía y gramática antes de entregar
Entregar tardeEl cliente pierde confianzaAcordar fecha de entrega y cumplirla

📄 10. Plantilla completa

📌 Usa esta estructura para tus informes:
  1. Portada: Logo, título, cliente, fecha, clasificación (Confidencial), versión
  2. Control de versiones: Tabla con versión, fecha, autor, cambios
  3. Índice automático
  4. Descargo de responsabilidad: Alcance, limitaciones, período de pruebas
  5. Resumen ejecutivo (1-2 páginas, lenguaje de negocio)
  6. Alcance: IPs, dominios, aplicaciones, redes probadas
  7. Metodología: OWASP, PTES, OSSTMM, o la que uses
  8. Resumen de hallazgos: Gráfica de pastel/barras por severidad
  9. Hallazgos detallados: Una ficha por vulnerabilidad
  10. Plan de remediación priorizado: Tabla con plazos
  11. Conclusiones
  12. Anexos: Herramientas usadas, logs completos, referencias
💡 Herramientas para generar informes:
  • Dradis: Plataforma colaborativa para reportes de pentest (open source)
  • PlexTrac: Plataforma comercial para gestión de reportes de seguridad
  • Ghostwriter: Herramienta de SpecterOps para reportes de Red Team (open source)
  • SysReptor: Generador de reportes de pentest basado en plantillas (open source)
  • Microsoft Word / LaTeX: El clásico, con plantillas bien diseñadas
